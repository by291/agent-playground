# Agent playground

An agent application that validates runtime capabilities while progressively strengthening its engineering foundations toward production use. Development prioritizes clear responsibilities, consistent state and recovery, explicit resource ownership, and regression coverage. The Python `agent_playground/` package defines a LangChain agent served by Aegra. The Hono `server/` exposes an AG-UI endpoint using the official remote LangGraph adapter. The React `web/` project provides chat, workflow review, and A2UI rendering.

```text
web/ (AG-UI client) → server/ (AG-UI adapter) → Aegra run queue → agent_playground/
                                                ↘ PostgreSQL checkpoints
```

## Project structure

| Area                            | Main modules                                                                                                                                                                                                                                                                                                                                                                                                                                |
| ------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `agent_playground/`             | Agent assembly, configuration, context, observability and HTTP entry points.                                                                                                                                                                                                                                                                                                                                                                |
| `agent_playground/workflows/`   | `experiment/`, `sql/` and `report/` own their workflow graphs, agent tools and cards; SQL state/contracts, revision agent and HTTP client are separate modules. `review.py` owns conversational review; `external.py` registers and waits for externally updated tasks; `output.py` publishes durable A2UI outputs and optional reply/presentation metadata.                                                                                |
| `agent_playground/services/`    | `sql/` owns SQL API request/response models, routes and validation; `report/` owns asynchronous report jobs, routes and background callback delivery. These local services simulate external APIs; SQL submissions are recorded without executing SQL.                                                                                                                                                                                      |
| `agent_playground/db/`          | SQLAlchemy contracts, application connection setup, workflow output storage and SQL receipt storage. Repositories do not depend on HTTP request/response types.                                                                                                                                                                                                                                                                             |
| `server/`                       | `app.ts` assembles the HTTP app; `http/` owns route handlers, request validation and conversation-change SSE; `server.ts` owns startup and shutdown; `agent/` owns the shared Aegra client, protocol adaptation and SSE transport; `conversation/` owns submission coordination, conditional run updates, checkpoint synchronization and read-only snapshots; `db/` owns the application database and schemas; `drizzle/` holds migrations. |
| `web/src/`                      | `app/` owns routes, environment configuration and global providers; `pages/` contains thin page entries and the development component workspace; `features/conversation/` owns conversation API, state, runtime and UI; `features/a2ui/` owns the shared catalog and ordered surface runtime; `components/ui/` holds shadcn/ui primitives; `styles/` owns theme and global styles.                                                          |
| `shared/`                       | The application run-status contract used by the TypeScript server and web app; reusable workflow review/output metadata contracts and the SQL business card schema and generic external-task status/update contract; protocol schemas remain owned by their official libraries.                                                                                                                                                             |

Service implementations depend on application configuration and database repositories. Workflows consume their HTTP APIs; the SQL client and workflow state reuse `services/sql/models.py` for API response contracts. Workflow revision output and checkpointed state remain in `workflows/sql/models.py`. The HTTP application owns service registration and the report and knowledge indexing worker lifecycles.

The [frontend architecture guide](docs/frontend-architecture.md) describes module boundaries, state ownership and frontend validation. The [conversation recovery design](docs/superpowers/specs/2026-09-27-conversation-recovery-design.md) describes the data and protocol boundaries. The [validation record](docs/conversation-recovery-validation.md) lists the local end-to-end checks and their limits.

The web app keeps shadcn/ui primitives in `web/src/components/ui/`. To add another primitive, run `pnpm dlx shadcn@latest add <component>` from `web/`; `components.json` keeps the registry settings. The A2UI workflow catalog uses its own React components on top of the official A2UI renderer.

Inter weights 400, 500, 600 and 700 are bundled locally through Fontsource; the app does not request Google Fonts at runtime. The development gallery loads Monaco's official editor feature registrations and JSON language support, with locally bundled workers.

Each conversation has its own Zustand store. Components subscribe to the fields they display, while `HttpAgent` manages the AG-UI stream. TanStack Query fetches and caches server snapshots by thread ID and refreshes after a run ends or the page regains focus. Newly created conversations accept input immediately and enable snapshot fetching after their first submission settles; restored conversations wait for an initial snapshot before accepting input. Two-second polling is enabled only for recovery while the page is focused: unfinished or unknown server runs without a live local stream, failed snapshot requests, a finished local run not yet present in the snapshot, or missing saved A2UI output. Idle conversations and healthy local streams do not poll. Saved conversations subscribe to `/conversations/:threadId/events`; PostgreSQL notifications invalidate their snapshot. SSE reconnect sends `ready` and fetches the full persisted state, and switching conversations closes the previous subscription. Snapshot requests are cancellable. The gateway health indicator refreshes every 30 seconds. The browser persists the thread pointer, an unconfirmed submission and an empty-conversation hint. A new or known empty conversation renders its welcome page immediately on reload; other conversations show a message skeleton while history recovers.

Query delivers each fresh result through the session once. The server synchronizes the latest run before reading its snapshot; completed and interrupted checkpoints are marked as synchronized in PostgreSQL, including their interrupts. Later polls read saved messages and outputs without re-fetching that checkpoint. Message synchronization inserts new IDs in one batch and saves their checkpoint order. Admission checks the newest run under the conversation lock; existing identical submissions are recognized before validating a new review, so a prepared review can be retried after restart. Run observations update only the state and Aegra mapping they originally read, so late callbacks and older upstream responses cannot reopen a terminal run. While a local request is submitting or streaming, a snapshot with an unconfirmed upstream mapping keeps that request's local run status; unknown-submission warnings apply after the local request is no longer active. Upstream and database failures return `503`; invalid submissions and admission conflicts return `400` or `409`.

## Conversation management

The sidebar lists saved conversations by the time of their latest submission, automatically loading older history when you reach the bottom, with an animated loading indicator and explicit retry on failure. Desktop rows use a compact 36px height; the scrollbar occupies the sidebar edge without an extra reserved gutter. A conversation appears after its first message is admitted; opening an empty conversation does not create a database row. The first user message supplies its title, up to 100 Unicode characters. Migration `0005` fills default titles from the first nonempty saved user message, including databases that already applied `0004`, and preserves custom titles. Select a row to restore its messages, tool process, workflow outputs and pending review. The row's action button provides **Rename** and a confirmed **Delete**; deleting the current conversation opens a fresh one. Unsent composer drafts and unsubmitted review edits belong to the open workspace and reset when switching conversations.

The address bar identifies a submitted conversation as `/c/<threadId>`. `/` opens a blank draft; opening the page, clicking New conversation, typing and selecting attachments do not allocate a thread ID or fetch a thread snapshot. The first valid message submission allocates the ID and replaces the draft URL without remounting the session. Attachments upload after this allocation and before submitting the message; an upload retry reuses the same thread and file IDs. Later messages reuse the conversation ID. Copy a saved conversation URL to open the same discussion in another browser; refresh, browser Back and Forward, and sidebar selection restore that conversation. These links open the live, editable conversation in the existing shared workspace. Save at least one message before sharing so the discussion exists on the server. Recipients need access to the same application server; a `localhost` URL works only on the sender's computer. A production web server must serve the SPA entry point for `/c/*` paths.

Switching conversations detaches the local stream while the server-owned Aegra run continues. Local storage retains each conversation's unconfirmed submission and empty hint separately so returning can recover the original admission without sending it again. The list refreshes on accepted runs, snapshot recovery, page focus and explicit refresh, without continuous list polling. `GET /conversations` returns pages of 30 summaries (`threadId`, `title`, `createdAt`, `updatedAt`, latest `status`) and an opaque `nextCursor`; pass it as the `cursor` query parameter. `PATCH /conversations/:threadId` accepts `{ "title": "..." }`, and `DELETE /conversations/:threadId` returns `204` on success. Invalid titles or cursors return `400`, and missing or deleted conversations return `404`.

Deletion is a soft delete: it hides the conversation and prevents further submissions or recovery, while retaining database records, workflow outputs and Aegra checkpoints. Prepared, dispatching, running and unconfirmed runs cannot be deleted (`409`); completed, failed and paused conversations can. Deletion and admission use the same conversation lock. History uses the current shared playground database; the gateway does not yet provide per-user authentication or ownership. Restarting the TypeScript server applies the migration automatically.

`DELETE /conversations` clears all saved conversations in the shared workspace, including history beyond the loaded sidebar pages. It returns `204` for a successful or already-empty batch. If any targeted conversation has an unfinished or unconfirmed latest run, the entire batch returns `409` without deleting anything. Bulk deletion uses the same soft-delete rules and admission locks; conversations created concurrently after the batch was selected are unaffected.

## Run locally

Requires Docker for PostgreSQL and Redis, plus uv, pnpm, Make, and a DeepSeek API key. The application processes run on the host for fast iteration.

```sh
make setup
# Set DEEPSEEK_API_KEY in the root .env file created by setup.
make dev
```

`make setup` creates three separate environment files: the root `.env` configures the Python agent and Aegra, `server/.env` configures the AG-UI server, and `web/.env` configures the Vite proxy. `make setup` generates the same random `WORKFLOW_API_TOKEN` in the root and server files for internal task registration. Each app reads its own file, and all three files are ignored by Git. For an existing checkout, run `node scripts/setup-env.mjs` before restarting; conflicting existing tokens are rejected.

The agent uses LangChain's `ChatDeepSeek` integration and defaults to `deepseek-flash`. Set `DEEPSEEK_API_KEY` in the root `.env`; `DEEPSEEK_MODEL` can override the model. `ChatDeepSeek` supplies the default API endpoint, and `DEEPSEEK_API_BASE` is only needed for a custom endpoint. If you already have a root `.env`, replace its old `OPENAI_*` entries with the `DEEPSEEK_*` entries from `.env.example`.

`make dev` waits for the infrastructure, starts the agent, server, and web app in the background, and then returns to the shell. Application logs and process IDs are stored in `.dev/`; use `tail -f .dev/*.log` to follow startup output. Run `make dev-stop` to stop all three application process groups; use `make infra-down` separately to stop PostgreSQL and Redis. To run a process in its own terminal instead, use:

```sh
make infra-up
make agent
make server
make web
```

Run the last three commands in separate terminals. Use `make infra-down` to stop PostgreSQL and Redis. Run `make help` to list the shortcuts.

From the repository root, `uv run agent` serves Aegra using `HOST` and `PORT` from the root `.env`, while `pnpm dev:server` and `pnpm dev:web` run the TypeScript apps using their local `.env` files. The Makefile forwards to these commands.

Open `http://127.0.0.1:5173` for the web UI. The AG-UI endpoint is `POST http://127.0.0.1:3000/agent`; the native Aegra API is on `http://127.0.0.1:2026`. PostgreSQL and Redis are exposed locally on ports `55432` and `56379`.

PostgreSQL keeps Aegra's service tables, Alembic history, checkpoints, and store in the `aegra` schema. The playground's conversation and workflow output tables use `public`. The TypeScript server applies its Drizzle migrations at startup; the Python graph prepares the workflow output table when it starts. Compose creates a local `aegra` database role with `search_path = aegra` when it initializes a new PostgreSQL volume; the existing `agent` role is used for application tables in `public`. Aegra uses `DATABASE_URL` from the root `.env` and should connect as `aegra`. Both the root `.env` and `server/.env` need their own `APP_DATABASE_URL` pointing to the application role.

PostgreSQL 18 mounts its data at `/var/lib/postgresql`; a volume initialized by PostgreSQL 17 cannot be reused. To recreate an older volume, run `docker compose down --volumes` followed by `make infra-up`. This deletes local PostgreSQL data.

The server creates Aegra runs via `@ag-ui/langgraph`. Agent execution goes through Aegra's queue and thread concurrency handling. Hono handles HTTP and SSE streaming. The React web UI uses `@ag-ui/client`, Tailwind CSS, shadcn/ui chat and form components, and Streamdown to render streaming Markdown alongside AG-UI events. Live assistant text uses a display buffer adapted from assistant-ui's smoothing scheduler, with a base rate of 60 characters per second, a 2.5-second adaptive backlog drain target, and at most about 30 display updates per second. The buffer continues draining for up to about 2.5 seconds after the model finishes; stored messages and run status retain the full received output. Restored history and tool commentary render immediately. New text uses Streamdown's native 500ms opacity fade with Unicode word segmentation. Only the current Markdown block animates, and older text in a long paragraph sheds its token spans so animation elements do not grow with the whole reply. The composer stays disabled until buffered text and the final fade settle. This presentation state is local to the UI and does not delay the persisted run status. Reduced-motion preferences disable both the display buffer and fades. The transcript follows new output while the reader is at the bottom, preserves the reading position when scrolled up, and offers a scroll-to-end button. The current server does not provide authentication or durable AG-UI event replay. It stores completed messages, workflow outputs, and run summaries so the UI can recover after a disconnect.

When the agent emits readable reasoning, the chat shows it in a **Thinking** / **Reasoning** fold beside the tool process. It opens during the active reasoning phase and folds when the first answer text is displayed, including when reply animation is enabled; an empty text-start event does not fold it. You can reopen it while the answer continues streaming, and later answer updates keep that choice. A live run that ends without an answer leaves its reasoning open. Restored replies start folded. Checkpoint recovery preserves DeepSeek `reasoning_content` and textual reasoning/thinking blocks as separate AG-UI reasoning messages for newly archived answers. Previously saved answers are not backfilled into a later turn; internal summarization messages and encrypted thinking are excluded. Models that do not emit reasoning keep the existing waiting indicator.

In development, **Activity** shows live AG-UI events observed by the SDK in the current page session, with millisecond receive times, step/tool names, run IDs and expandable complete event JSON. Run boundaries have labeled dividers in both merged and individual-event views; events remain newest first. **Merge stream content** is on by default: text, reasoning and tool-argument deltas are combined in receive order within their run and message/tool-call boundaries, and update while streaming. The merged view shows retained content and lets you expand its original events; turn merging off to inspect each delta separately. Missing start or closing boundaries are marked as partial content rather than presented as a complete transcript. Other event types remain individual. Event categories have distinct labels, icons and theme-aware colors; JSON syntax highlighting runs only while a detail is expanded and preserves the received values. JSON retains its indentation and scrolls horizontally for long lines. On wide desktops the panel defaults to 520 pixels and its left separator resizes it between 400 and 720 pixels, with arrow keys, Home and End as keyboard alternatives. Its width is saved separately from the sidebar width in the current browser. Below the side-by-side breakpoint the panel fills the available workspace and hides the resize handle.

**Copy log** always includes all retained original events in receive order, alongside the latest run summary and current client issues, regardless of the selected view. Transport, recovery and output errors appear separately as client issues, including failures before any protocol event arrives. The badge counts events received since the last **Clear log**, while the panel separately shows how many remain in the 500-event buffer and marks logs that have discarded older events. Clearing the log does not alter conversation data, clear client issues or stop a run. Events are not persisted or reconstructed from saved messages: refreshing or switching conversations clears the log.

The events have already passed through the gateway's protocol adapter and filtering and the SDK's validation and normalization; rejected events are not captured, and this panel is not a byte-level SSE or raw Aegra trace.

## Call the AG-UI endpoint

```sh
curl --no-buffer -X POST http://127.0.0.1:3000/agent \
  -H 'Content-Type: application/json' \
  -H 'Accept: text/event-stream' \
  -d '{
    "threadId": "8af32af0-715d-47be-a4a2-0678a532e5da",
    "runId": "b50da20d-b907-43dd-a284-d88995796b9e",
    "messages": [{"id": "2e455cc4-7507-4c9e-95f9-a785e08c5abb", "role": "user", "content": "What time is it now?"}],
    "tools": [],
    "context": [],
    "state": {}
  }'
```

The original `get_current_time` tool is still built into the agent. The local MCP server exposes `calculate_sum`; Aegra loads it through the LangChain MCP adapter when the graph starts. The `run_experiment_workflow` tool runs a small LangGraph workflow with visible steps and one human review point. Try "Use the MCP tool to add 12 and 30" or "Create an experiment plan for testing an agent workflow" in the web UI.

Each workflow step emits an A2UI v0.9 surface: captured idea, draft plan, review request, and review result. The review step also pauses with a LangGraph interrupt. The AG-UI adapter exposes the pause through `RUN_FINISHED.outcome`; the web UI lets you edit and approve the draft or reject it, then resumes the same thread with `resume[]`.

The chat shows one current experiment-plan card per workflow tool call. Earlier stage surfaces stay available inside the tool process. While review is pending, editable title and steps replace the review-request card, with direct **Approve plan** and **Reject** actions. Parallel plans require an explicit decision for each plan before **Continue workflow** submits the batch. The reviewed result replaces the editor in the same reply, including after refresh; subsequent model replies briefly acknowledge the outcome instead of repeating the plan. Saved node outputs keep their original A2UI payloads so existing conversations can still recover and resume.

The [workflow mechanisms guide](docs/workflow-mechanisms.md) explains how business workflows reuse review, feedback, reply archiving and artifact history.

The additional `run_sql_workflow` tool demonstrates a conversational SQL review loop without changing the experiment workflow. Click **Review SQL** on the welcome screen to prepare an editable example request, then send it to start. You can also try **"Use run_sql_workflow to calculate monthly revenue from paid orders."** It calls the local `/sql-demo/generate` API for a deliberately imperfect SQL and a fixed PostgreSQL `orders(id, customer_id, created_at, status, amount)` schema, then `/sql-demo/check`. When the initial check fails, an agent proposes one revision and the workflow rechecks it before pausing. Continue typing in the chat to request changes or explanations. SQL changes increment its version and require another check; explanations preserve the version and its check. **Accept and submit** is available only when the current SQL passed its check. **Abandon** ends the workflow without submitting. Each review round has a separate persisted output, and refresh restores the latest SQL, checks, discussion and pending decision. Prior SQL cards are available inside the original tool process. When several reviews are pending, decide on individual SQL workflows or the experiment batch first; chat feedback is enabled only for one unambiguous SQL review.

The SQL APIs are a simulation: generation always starts from `SELECT * FROM orders;`, and the real configured model adapts it to your request using the provided schema. Checks use sqlglot for parsing, single-SELECT, explicit-column and demo-schema validation; they do not run PostgreSQL, verify query semantics, inspect query plans or prove performance. `/sql-demo/submit` rechecks the accepted SQL and stores an idempotent receipt in the Python-owned `sql_demo_submissions` table; it **never executes SQL**. Receipt keys include conversation, workflow call and accepted revision identity. `/sql-demo/submissions/:id` recovers receipts after a transport failure. SQL revisions use the configured model with DeepSeek thinking disabled locally because forced structured-output tool choice is incompatible with thinking mode; the parent chat model configuration is unchanged. Set `SQL_DEMO_API_URL` in the root `.env` if Aegra runs at a different address; it defaults to `http://127.0.0.1:2026/sql-demo`. These local demonstration endpoints share the playground's current lack of authentication and are not a production SQL submission service.

The `run_report_workflow` tool demonstrates the reusable external-task mechanism. Click **Generate report** and send its prepared request. The simulated API returns `202` immediately, then independently delivers queued, preparing, processing, finalizing and completed states over approximately 12 seconds. Task status, progress and history update live. You can close or switch away from the conversation: the server resumes the waiting LangGraph workflow on success or failure, publishes its result and archives the parent agent's reply without a browser. Reopening restores the saved result. To exercise failure, ask the agent to run the report workflow with `outcome="failed"`.

Other business workflows use `register_external_task()` before submitting their API job, forward the returned per-task callback credential to that trusted service, then call `wait_for_external_task()` in a separate node. The internal registry is `POST /internal/external-tasks` with `Authorization: Bearer <WORKFLOW_API_TOKEN>`. An external service posts snapshots to `POST /external-tasks/:taskId/events` using its task callback token and `{revision, status, stage, message, progress?, result?, error?}`. Status is `queued`, `running`, `succeeded` or `failed`; success requires an object result and failure requires an error. Increasing revisions are saved with history; exact duplicates and older updates are ignored, conflicting same-revision updates and changes after terminal status return `409`. Task credentials are excluded from conversation snapshots. Progress updates do not run the model. Terminal callbacks arriving before the wait checkpoint are retained until that checkpoint is ready.

The conversation-owned worker bounds each upstream request to 10 seconds and aborts its in-flight requests during shutdown. It scans persistent tasks every second, admits continuation under the existing conversation lock and starts a native Aegra run without an SSE consumer. Ambiguous upstream creation uses the existing mapping reconciliation and never blindly creates another run; a persistently unconfirmed continuation remains `submission_unknown` and requires manual reconciliation. The external wait locks the composer in that conversation; concurrent user turns, explicit task cancellation and automatic external-task timeouts are not implemented. Deleting a paused conversation prevents new continuation and callbacks; it does not cancel an already submitted external job. The local simulator stops callback delivery after `404`, persists its delivery offset and resumes unfinished jobs after restart. It is a demonstration API, not a production external worker.

Set `APP_API_URL` (formerly `WORKFLOW_API_URL`) in the root `.env` when the server is not at `http://127.0.0.1:3000`, and `REPORT_DEMO_API_URL` when the simulator is not at `http://127.0.0.1:2026/report-demo`. Registration and business API submission need stable identities; each real external service must support idempotent job creation or its own unknown-outcome recovery. PostgreSQL owns durable task state; notifications are invalidations rather than a replayable event log. The dedicated conversation SSE subscription displays updates from workflows and background continuations, while ordinary model text still uses AG-UI streaming.

Python constructs the official `{ messages: [...] }` model and saves each output before emitting an AG-UI `CUSTOM` event named `a2ui`. Its value contains `id`, `outputSeq`, run/tool ownership and the standard `messages` array. Conversational workflows can add `workflow.reply` and `workflow.presentation` metadata for public replies, card grouping and reply ownership without embedding those mechanisms in business components. The server forwards the event and exposes saved outputs through `GET /conversations/:threadId`. One official `MessageProcessor` per web conversation consumes both sources in `outputSeq` order, deduplicates repeated outputs, and supports multiple surfaces, component/data updates and deletion. `WorkflowText` supports official dynamic string bindings such as `{ "path": "/title" }`. The renderer uses the custom workflow catalog and official React surface renderer. Sequence gaps trigger snapshot recovery; malformed or conflicting output displays an error. Because the processor does not roll back a failed batch, affected surfaces are hidden and further A2UI processing stops for that conversation session.

In development, **Components** in the chat header opens `/dev/a2ui-components` in a new tab. Choose a registered component with the shared Select control and edit its JSON example in the local Monaco editor; the adjacent preview updates from valid A2UI JSON. Chat and component pages have distinct browser-tab titles and share the app icon. **Activity** is also development-only. Production builds omit both controls and the component gallery. Example files live in `web/src/pages/dev/a2ui-components/examples/`. The preview requires a complete surface with a root component and keeps the last valid result while JSON is invalid. Conversation ingestion also accepts update-only batches. A2UI actions are not connected to the backend; review submission continues to use the separate review form.

Each component keeps its schema and renderer together in `web/src/features/a2ui/catalog/components/`; `catalog/index.tsx` registers them. The gallery owns preview models and releases them on replacement, reset and unmount. A2UI ingestion distinguishes ready, waiting and failed results: a sequence gap that recovers successfully does not mark the submission trace as an error.

The current output format has version 3. Legacy `kind: "a2ui"` wrappers, `experiment_card` events and Basic Catalog surfaces are unsupported. Existing database rows are retained; conversations using those unsupported formats require a new conversation. SQL conversations from before the shared review refactor are unsupported and should be deleted; new conversations use `workflow_review` and independent reply/presentation metadata. Local storage holds the current thread pointer and each conversation's empty hint and unconfirmed submission for retry. A disconnected browser does not cancel the Aegra run. If a server crash leaves Aegra run creation unconfirmed, the server checks only the newest Aegra run for that thread. When it cannot confirm the mapping, the submission becomes `submission_unknown` and the UI does not resend it. Later polls can recover a mapping confirmed by that same bounded lookup; a persistently unconfirmed submission requires manual reconciliation. Aegra's native Agent Protocol stream is also available at `POST /runs/stream` on port `2026`.

The chat workspace uses a neutral graphite theme with a collapsible desktop sidebar. Its default width is 320px; drag the right edge or use the separator's arrow keys to adjust it between 240px and 420px. The browser remembers both the chosen width and whether the sidebar is collapsed. Width changes follow the pointer directly. Collapsing and expanding coordinate the sidebar width, labels, and buttons with a short transition that respects reduced-motion preferences. Conversation content and the composer share a centered column up to 896px wide, with assistant avatars in the left gutter. Markdown code blocks include syntax highlighting and a compact toolbar for copying or downloading the original source. On smaller screens, the navigation button opens a modal drawer that can be closed with its close button, Escape, or the backdrop. Changing the sidebar layout preserves composer drafts and review edits. Welcome suggestions prepare an editable draft; sending the draft starts the run. Connection status lives in the sidebar, development tools remain in the header, and the context ring sits beside the send button with the configured model name.

The settings button beside the gateway status opens workspace preferences on desktop, collapsed navigation and mobile. Choose Light, Dark or System appearance, Enter or Ctrl/Cmd + Enter to send, and whether replies use the paced reveal and fade. Shift + Enter always inserts a new line, and composition input does not submit. Reply animation continues to respect the system reduced-motion preference. Changes apply immediately and are saved in this browser; resetting preferences leaves conversations and navigation layout intact.

Settings also provides **Clear all conversations**, which opens a separate confirmation dialog above settings and explains its shared-workspace scope. Cancel, Escape or clicking its backdrop returns to the unchanged settings window. Success closes only the confirmation dialog, keeps settings open and opens a fresh conversation behind it, while clearing cached snapshots and browser conversation pointers and preserving preferences and navigation layout. A rejected request leaves the current discussion and history intact and displays the server's reason in the confirmation dialog. Cleared conversations cannot be restored through the app.

## Context management

The agent uses LangChain's `SummarizationMiddleware` to compact older messages automatically when estimated context usage reaches 80% of the model window. It retains recent messages within a 20% token budget, preserving tool-call/result pairs, and replaces earlier history with a summary saved in the checkpoint. The summarization call receives all selected history without the middleware's default 4,000-token truncation. It uses the same DeepSeek model with thinking disabled and a 4,096-token output limit; summary failures propagate without replacing history. A single oversized turn that still exceeds the window after compaction is rejected rather than silently truncated.

The root `.env` can override `CONTEXT_COMPACT_RATIO` (greater than `0.2` and less than `1`) and `CONTEXT_WINDOW_TOKENS`. The window otherwise comes from LangChain's model profile; a custom DeepSeek model without a profile requires an explicit window. Changing these settings requires restarting the agent.

The model control beside the send button opens estimated token usage and a breakdown of system instructions, tool definitions, conversation messages (including tool-call arguments), tool results, and summaries. Counts use LangChain's approximate counter with a conservative two-character-per-token ratio; they are estimates, including for Chinese text, rather than an exact tokenizer or billing measurement. Provider-reported input tokens from the last model request are shown separately when available. Usage refreshes at model boundaries, so text still streaming and unsent composer input are not yet counted. The model name is available before the first turn through a read-only `GET /agent-info` route: Python reads the same configuration as the graph, and the TypeScript server forwards that metadata. Stored usage from a different model is hidden until the current model reports fresh usage.

The browser sends only the newest user message for a normal turn. Aegra's checkpoint owns model history; archived chat is not reintroduced after compaction. The complete public transcript is kept separately in the application database. Internal summaries and compressed message snapshots do not replace that transcript. Current-run replies are kept in checkpoint state until synchronization so compaction during a tool loop cannot erase recoverable replies. Context usage is synchronized with the latest finished or interrupted checkpoint and recovered after reload without extra upstream reads on every poll.

## Shared knowledge

Open **Knowledge** in the chat sidebar to upload TXT, Markdown or text PDFs. Documents are shared across conversations. Uploads are limited to 10 MiB; PDF extraction supports up to 200 unencrypted pages and two million extracted characters. Scanned PDFs need OCR before upload.

Configure embeddings independently of DeepSeek in the root `.env`:

```dotenv
RAG_EMBEDDING_BASE_URL=https://your-provider.example/v1
RAG_EMBEDDING_MODEL=your-embedding-model
RAG_EMBEDDING_API_KEY=your-key
RAG_EMBEDDING_BATCH_SIZE=10
# Optional, only if your provider supports dimensions:
RAG_EMBEDDING_DIMENSIONS=
RAG_MAX_DISTANCE=0.55
```

`RAG_MAX_DISTANCE` is the maximum cosine distance accepted as evidence, from 0 to 2. A lower value requires a closer match. The adapter sends text inputs to the OpenAI-compatible `/embeddings` endpoint. `RAG_EMBEDDING_BATCH_SIZE` controls the number of texts per request and defaults to 10; it does not change text chunking or the embedding profile. Qwen `qwen3.7-text-embedding-flash` accepts up to 20 texts per request, while `text-embedding-v3/v4` accept up to 10 ([provider API limits](https://help.aliyun.com/zh/model-studio/text-embedding-synchronous-api/)). Set the batch size to your configured model's limit; the Qwen example configuration uses 20. Missing configuration produces an indexing error with a retry action; no substitute embeddings are used. Restart the agent after changing these settings, then use **Reindex** for existing documents. Endpoint, model and dimension changes use a separate index profile.

The TypeScript server stores original bytes in the configured S3 bucket and applies document/chunk migrations in `public`. Shared file storage now uses `S3_ENDPOINT`, `S3_BUCKET`, `S3_REGION`, `S3_FORCE_PATH_STYLE` and the AWS SDK credential chain in `server/.env`; existing `SKILL_S3_*` settings must be renamed to `S3_*`. Skills and Knowledge share this client and bucket, with separate object keys. Compose uses PostgreSQL 18 with pgvector; the existing PostgreSQL 18 volume is retained.

The Python HTTP application runs the durable indexing worker. It downloads originals through the authenticated internal application route, extracts text with pypdf in an owned subprocess, splits with LangChain, calls embeddings and stages pgvector chunks. Each attempt has a two-minute deadline and a three-minute lease. Expired jobs are reclaimed after restart; only the current generation can publish a ready index. Failed jobs can be retried from the page. Incomplete uploads can resume with the same original file. Reindexing immediately hides the previous chunks.

Ask the agent a question about the uploaded documents or shared knowledge base. `search_knowledge` returns up to five matching excerpts from ready documents under the current embedding profile, each with a citation Markdown link bound to its chunk ID. New answers are instructed to place that exact link after the supported sentence or paragraph. The interface renders it as a numbered footnote: clicking opens that precise excerpt, filename and PDF page in the side reader, while closing returns focus to the citation. Repeated retrievals of a chunk share its number within a reply; references absent from that reply's retrieved sources display as unavailable. Citation associations express the model's choice of evidence, without automatically verifying that the excerpt supports its claim.

The compact **Sources** button opens the same reader for all retrieved passages, including older answers without inline citations. A single document displays its filename; multiple documents use the shared document selector. Move between retrieved passages and download the original; sources and inline citations remain available after reloading a conversation. Searches with no evidence are shown explicitly.

Deleting a document immediately hides its index and download. The server independently retries S3 cleanup and removes chunks. It also scans one `knowledge/` object-list page per cleanup pass to remove uploads that finish remotely after a client timeout; S3 credentials need list, get, put and delete permissions for these objects. A small metadata tombstone prevents delayed upload retries from recreating deleted document IDs. Conversation deletion does not delete shared documents; previously saved conversation excerpts remain part of that conversation's history.

The document API is `/api/knowledge/documents` (list/upload), `/:id/reindex`, `/:id` (delete) and `/:id/file` (download). The initial implementation uses exact cosine search without an ANN index. It has no OCR, tenant permissions or document version catalog. Controlled-provider tests verify the HTTP, S3, Python worker, pgvector and restored-source chain; real-provider/model validation requires your configured credentials.

## Tool process in chat

Each user turn has one assistant reply area. Tool calls appear in a collapsed process above the final answer. Expanding the process shows the assistant's accompanying text and each tool's execution status; expanding a tool shows its parameters and raw result. This text is ordinary assistant content, not private reasoning. A user-opened process stays open when the run finishes. Tool failures remain visible while collapsed, and workflow cards and review forms remain directly accessible outside the process.

Assistant tool calls and tool results are archived as official AG-UI messages in `conversation_messages`, including empty assistant messages that contain tool calls. The Python checkpoint keeps these public messages recoverable across context compaction and review resumes. Refresh restores the saved process, initially collapsed. Previously archived text-only replies still share one assistant area, but their missing tool metadata is not reconstructed from text.

```sh

```

`make check` runs Pyrefly and TypeScript type checking, Ruff and ESLint linting, Ruff and Prettier format checks, Python, server and web tests, and the web build. `make format` applies the Python and frontend formatters. Individual targets such as `make typecheck`, `make lint`, `make format-check`, `make test`, and `make build` are available when a faster check is useful. Web linting checks Tailwind class names, including canonical forms such as `max-w-205`.

GitHub Actions runs the Python, server, web, and browser E2E checks in parallel for pull requests and pushes to `main`. The Python job uses Testcontainers and needs no DeepSeek API key.

Pyrefly uses its strict preset. Ruff keeps its default checks and adds import sorting, common bug checks, and Python syntax upgrades; its formatter uses the default 88-character line length. Both TypeScript projects enable strict checking, unchecked index access, exact optional properties, and verbatim module syntax. ESLint uses the JavaScript and type-aware TypeScript recommended rules, with React Hooks rules for the web app. Prettier uses its defaults, while `.editorconfig` defines indentation and line endings for editors.

The Python and server PostgreSQL tests use Testcontainers to start temporary `pgvector/pgvector:0.8.7-pg18` containers. Ordinary Python database tests share one session container with a fresh database per test; server integration tests share one project container with a fresh database per file. Tests close their connections before dropping these databases, so leaked connections fail teardown. The Python worker tracing test owns separate PostgreSQL and Redis containers for its worker-specific setup. `make test` and `make check` need a running Docker daemon, but do not need the Compose database or a `TEST_DATABASE_URL` variable.

TypeScript unit, integration, and DOM interaction tests use Vitest. `pnpm test` runs these server and web tests, including the PostgreSQL integration suite. Server tests use the Node environment. Web tests use the threads pool and reuse each worker's module graph and environment in the `shared` project; App route tests run in the `isolated` project because they change development mode before importing configuration. DOM tests opt into jsdom and use React Testing Library with jest-dom assertions. The web test setup releases mounted components, resets browser storage and appearance, and restores mocks and timers after each test. Tests must release listeners and other owned resources and use restorable mocks for global overrides. Type checking remains a separate `pnpm check` step.

When changing shared test state, check file-order independence with a single worker, for example `pnpm --filter agent-playground-web exec vitest run --maxWorkers 1 --sequence.shuffle --sequence.seed 104`, then repeat with a different seed. Tests that require fresh import-time configuration belong in the isolated project.

`pnpm test:e2e` needs Docker and the root Python environment prepared by `uv sync`. Browser requests pass through the real frontend, AG-UI adapter, API and database. Playwright owns the servers, and the harness releases its containers, Python process and connections on shutdown. Tests cover welcome restoration, tool details, streamed code and copying, reload during a run, edited workflow approval, sidebar resizing, live external-task progress, browser-independent continuation, shared knowledge indexing/retrieval and the development gallery. The shared browser fixture disables reply animation and uses reduced motion for ordinary functional tests. ## Agent Skills

项目维护者可以在 `skills/<name>/` 发布标准 `SKILL.md`，并附带 `scripts/`、`references/` 和 `assets/`。Agent 先看到名称和描述，按请求自动选择或响应显式 `$skill-name`，再用 `load_skill` 读取说明、`read_skill_file` 读取资源、`run_skill_script` 执行已发布的 Python、Bash 或 Node 脚本。新增或修改 Skill 后重启 agent；普通聊天用户上传的是输入文件。

对话中的 Skill 调用按 Skill 名称单独展示，带 `Skill` 标识和执行状态；展开后显示脚本或资源路径，并可检查调用参数和结果。普通工具使用同一套样式，带 `Tool` 标识、工具名称和执行状态；多个工具调用显示数量，展开后查看各项详情。实时回复和恢复后的历史使用相同的展示方式。

```bash
# Existing checkouts: add the S3 settings from server/.env.example to server/.env.
make dev
make skills-smoke
```

`make dev` / `make infra-up` 默认启动 PostgreSQL、Redis、OpenSandbox 控制服务和 SeaweedFS 单节点 S3，并构建包含 Python、Bash、Node、httpx、pandas、openpyxl 和 pypdf 的执行镜像。SeaweedFS 的本地开发凭据见 `infra/skills/s3.json`，只映射 localhost 的 8333 端口，内容持久化在 Compose volume。这套配置用于本地试用。已有 S3 兼容服务可配置 `server/.env` 中的 `S3_ENDPOINT`、`S3_BUCKET`、`S3_REGION` 和 `S3_FORCE_PATH_STYLE`；bucket 需要事先创建。凭据使用 AWS SDK 标准 credential chain，例如服务器环境中的 `AWS_ACCESS_KEY_ID`、`AWS_SECRET_ACCESS_KEY`、可选 `AWS_SESSION_TOKEN`，或部署环境提供的 role。S3 凭据不传给浏览器或脚本。

输入框的 **Attach files** 可选择最多四个文件，每个不超过 10 MiB。文件内容通过后端写入 S3；PG 仅保存对象 key、摘要、大小、发布状态和会话归属，每个会话最多 100 MiB。上传失败保留草稿和文件选择，相同 ID/内容可重试，冲突内容返回 409。未完成的上传保留元数据但不可下载，直到重试成功或删除会话。内部文件接口沿用 `WORKFLOW_API_TOKEN`，脚本输入按当前会话校验，输出还需对应已有 run。输出声明相对 `/workspace` 的路径，工具结果中的文件会在聊天里显示下载链接，刷新后仍可下载。删除会话立即撤销下载访问，后端每 30 秒清理已删除会话的 S3 对象；失败时保留元数据，下次或重启后继续。应用保留当前共享工作区访问模型。

可以发送 **"$csv-summary Summarize the sample CSV and provide summary.json."**，或附上 CSV 后发送 **"$csv-summary Summarize the attached file."**。`http-query` 示例对 `https://httpbin.org/get` 发起 GET 并提供 JSON 文件。

每个 Aegra worker execution 延迟创建一个 Docker 沙箱，多个脚本调用共享 `/workspace`，执行结束、失败或取消时销毁；进程崩溃后由 20 分钟 TTL 回收。下一轮聊天或人工审核后的恢复创建新工作区，需要重新传入文件 ID。脚本以 UID 1000 运行，限制为 1 CPU、512 MiB、256 个进程，每次最多 120 秒、四个声明输出，各 10 MiB，日志合计最多 64 KiB。Skill 内容以只读文件发布，脚本不挂载仓库、宿主文件或 Docker socket。OpenSandbox 控制服务持有 Docker socket，其 API 和动态执行端口均限制到 localhost。本地使用 OpenSandbox 官方 `release-1.1.1-rc.1` 镜像，通过 `[docker] publish_host = "127.0.0.1"` 原生配置限制动态端口，无启动补丁；真实 smoke 会检查容器的实际端口绑定。该版本为预发布版：1.1.0 的 PyPI 包缺少生成模块，且尚无此端口配置。停止基础设施前先用 `make dev-stop` 结束应用执行，再用 `make infra-down` 停止基础设施。

根 `.env` 中 `SKILL_ALLOWED_HOSTS` 设置允许的出站域名，默认仅 `httpbin.org`；`SKILL_SCRIPT_ENV` 显式列出要传给脚本的环境变量名称。镜像依赖由维护者构建，脚本不会继承整个 agent 环境。只允许执行 bundle 内 `scripts/` 下的 `.py`、`.sh`、`.js`，参数作为字面量传入；本版没有任意代码执行工具、跨轮工作区或 Skill 上传市场。外部 API 写入仍需业务 API 的幂等和结果确认，超时或失败不会自动重试。域名规则不限制 HTTP 方法，Docker 容器隔离也不是针对不可信多租户的 VM 边界。
